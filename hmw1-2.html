📚 Project Description & Wallet Pipeline

Wallets such as MetaMask, Rabby, Rainbow and Exodus do not ask users to memorize 256-bit keys. They chain several standards, each solving a different problem. This page implements the whole chain in the browser (PBKDF2, HMAC-SHA512, BIP-32 child derivation, secp256k1, Keccak-256, EIP-55) and verifies it against a well-known test vector.

Entropy → BIP-39 mnemonic → PBKDF2 seed (512 bit) → BIP-32/44 private key (256 bit) → secp256k1 public key (x‖y, 512 bit) → Keccak-256 → last 20 bytes → EIP-55 checksummed address

Why several primitives? BIP-39/32/44 manage and derive keys; secp256k1 links private and public key and enables digital signatures; Keccak-256 hashes; EIP-55 detects typing errors; hexadecimal is only an encoding. None can replace the others.

Distinctions required by the assignment

  • Key generation vs key derivation: generation draws fresh random entropy. Derivation deterministically expands an existing secret (seed → child keys). Losing the seed loses every derived key. Anyone knowing it can recompute them all.
  • Public-key cryptography: secp256k1. Easy forward (k→kG), hard backward (ECDLP, about 2128 steps).
  • Hashing: Keccak-256. Keyless, one-way, no inverse structure.
  • Checksums: EIP-55 (and the 4-bit BIP-39 checksum). Detect accidental errors only.
  • Encoding: hex and word lists. Reversible by anyone.

How the steps fit together

  • Authenticity & integrity: only the holder of k can produce valid ECDSA signatures.
  • Public key hidden behind a hash: the address is a hash of Q. The public key becomes visible only after the first outgoing transaction, which gives some extra margin against hypothetical future attacks on the curve.
  • Typing safety: an EIP-55 address with L letters misses a random error with probability about 2−L. With about 15 letters on average this is roughly 99.997% detection.
  • Hardened vs normal derivation: hardened children use the private key in the HMAC, so a leaked child key plus the parent public key cannot reveal the parent key. Normal children can be derived from the public key alone (watch-only wallets).

Temporal timeline & historical evolution

1977
RSA
First practical public-key scheme, based on integer factorization. Needs 2048+ bit keys; elliptic curves later gave comparable security with 256 bits.
2001
SHA-2 / SHA-512 standardized
Merkle–Damgård family from NIST. SHA-512 powers HMAC and PBKDF2 inside BIP-32 and BIP-39.
2012
BIP-32 (HD wallets) · Keccak wins the SHA-3 competition
BIP-32 (Pieter Wuille) replaces single-key wallets with a tree of keys from one seed. In the same year NIST selects Keccak as the future SHA-3.
2013
BIP-39 (mnemonic code)
Entropy plus checksum encoded as 12–24 words from a 2048-word list; seed via PBKDF2-HMAC-SHA512.
2014
BIP-44 (multi-account paths)
m / purpose' / coin_type' / account' / change / address_index, with coin type 60 for Ethereum. Ethereum is finalized with the original Keccak.
August 2015
SHA-3 (FIPS 202)
Keccak is standardized as SHA-3, with a different domain-separation byte, so SHA3-256 differs from Ethereum’s Keccak-256.
2016
EIP-55 (mixed-case checksum)
Proposed by Vitalik Buterin: a backward-compatible checksum hidden in the capitalization of the address.

SHA-2 / SHA-512 vs Keccak / SHA-3

Both are cryptographic hash functions, but with different internals: SHA-2 uses the Merkle–Damgård construction, Keccak/SHA-3 the sponge construction. Ethereum uses the original Keccak-256 (padding byte 0x01), while NIST’s SHA3-256 appends the domain-separation bits 01 before the padding (byte 0x06). Same permutation, different outputs. Key generation: BIP-39 entropy → mnemonic indices

Generates fresh 128-bit entropy with the browser CSPRNG, appends the first 4 bits of SHA-256 as checksum and splits the 132 bits into twelve 11-bit indices. Each index selects one word of the 2048-word BIP-39 list (the list itself is not embedded here).
